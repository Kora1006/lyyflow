# /lyyflow:specs —— 技术方案阶段

## 输入
`$ARGUMENTS`：
- 指定 spec（如 `spec-001` 或名称）→ 只处理该 spec
- 留空 → 处理 `specs/` 下所有状态为「待方案」或「方案待修正」的 spec

## 前置
先读取 `specs/overview.md` 和目标 spec 文件，确认需求与涉及的端/项目。若 `specs/` 不存在，提示用户先运行 `/lyyflow:prd`。

## 目标
针对每个 spec，分析 **需要改动的内容** 并给出 **可落地的技术方案**，写入 spec 文件。本阶段**不写实现代码**（那是 /lyyflow:ai 的任务），但要把「怎么改」讲清楚、落到具体文件和接口。

## 执行步骤（对每个 spec）

### 1. 读取/生成项目规则文件 CLAUDE-RULE.md
进入该 spec 涉及的端/项目根目录后：
- 若项目根目录已存在 `CLAUDE-RULE.md`，先**通读**它（描述了项目结构、技术栈、公共组件、命名/目录约定、请求/状态管理等），作为后续定位代码和定方案的依据。
- 若**不存在**，则先**生成**一份 `CLAUDE-RULE.md`（分析 `package.json`/构建配置/源码结构等得出），内容覆盖：项目结构、技术栈与版本、目录与命名约定、公共组件/工具、接口请求方式、状态管理、规范/约束等，便于本设备及下次执行直接阅读。生成后简要告知用户。**末尾双引用**：`@.lyyflow-local/lessons-learned.md`（主路径,本地教训,优先读）+ `@specs/lessons-learned.md`（公开快照,兜底）。
- 涉及多端时，**每端各自**的项目都要处理其 `CLAUDE-RULE.md`。

### 2. 定位代码
用 Glob/Grep 在涉及的端/项目中找到相关模块、组件、页面、接口、数据模型、路由、状态管理。

### 3. 分析改动点
逐条对应 spec 的需求，说明：
- 要改哪些文件 / 新增哪些文件
- 涉及的接口（前端调用、后端提供）是否已存在，是否需新增
- 涉及的埋点事件是否已定义，是否需新增（对照 `specs/tracking-events.md`）
- 数据流、状态、路由的变化
- 多端共享的逻辑（接口契约、常量、类型定义）是否需要统一

### 4. 给出技术方案
- 选型与取舍（多方案时给出推荐并说明理由）
- 关键实现思路（伪代码或结构草图即可）
- 对现有功能的影响 / 回归风险
- 需要其他端/服务配合的事项
- 埋点方案：每个埋点事件的具体调用位置、参数、触发条件

### 5. 写入 spec 文件
追加 `## 技术方案` 章节（见下模板），并把状态改为「待实现」。

> **提示**：如本 spec 改动风险等级明确（纯重构/纯样式 / 涉及鉴权/契约），可在 `## 技术方案` 里加 `### 审核策略（可选）` 字段强制 `/lyyflow:review` 走特定 tier；不填则由 Jev 自动路由。

### 6. 同步更新状态
更新 `specs/overview.md` 的状态看板和「当前进度」章节。

## 技术方案章节模板

```
## 技术方案

### 改动点清单
| 文件/模块 | 端 | 改动类型 | 说明 |
| --- | --- | --- | --- |
| src/xxx.vue | H5 | 修改 | ... |
| pages/yyy/index | 小程序 | 新增 | ... |

### 不在范围内
- xxx 功能暂不处理（原因：...）
- yyy 优化后续迭代（原因：...）

### 方案
<推荐方案及理由，关键实现思路>

### 接口契约（如涉及）
- 路径、方法、请求/响应结构；是否复用已有接口

### 埋点方案（如涉及）
- 埋点事件清单：

| 事件名称 | 事件类型 | key | moduleId | featureId | pageId | attr | 触发时机 | 文件位置 |
|----------|----------|-----|----------|-----------|--------|------|----------|----------|
| <名称>   | EXP/CLK  | <编码> | <模块ID> | <功能ID> | <页面ID> | <动态属性> | <何时触发> | <哪个文件哪行> |

- 埋点调用方式：`qt.QTEventTracking({ event: { key, moduleId, featureId, attr }, common: { page: { pageId } } })`（对齐项目既有埋点模式）
- 注意事项：<如：需先判断 qt 是否存在、attr 动态属性来源等>

### 风险与影响
- 回归范围、兼容性、性能

### 审核策略（可选，**默认留空**让 Jev 自动路由）

> 该字段供 `/lyyflow:review` Step 0 路由判定使用。**不填 = 走 Jev 自动选择**；填了 = 强制覆盖。
> 只在以下情况手工指定：① 改动很小但 Jev 误判（强制 trivial） ② 改动看着简单但涉及鉴权/契约（强制 core） ③ 临时禁用 Jev（强制 standard 或 core 走 Codex）。

- 期望层级: <core | standard | trivial>
- 理由: <可选，说明为什么强制覆盖>

> **典型场景**：
> - 纯重命名/重构/样式调整 → `trivial`（用 Jev 轻校验，节省 Codex 配额）
> - 普通功能需求 → 留空（让 Jev 判定，多数会走 standard）
> - 涉及鉴权/支付/接口契约/并发 → `core`（强制 Codex 全套 review + adversarial）
```

## 异常流转

当出现以下情况时，按对应流程处理：

### 方案待修正状态
如果 spec 状态为「方案待修正」（通常是 review 或实现阶段发现问题），在本阶段：
1. 先读取该 spec 的「实现记录」或「审核结论」，了解问题所在
2. 更新技术方案（修正原方案或提出新方案）
3. 状态改为「待实现」，清空或备注之前的实现记录

### 发现需求问题
如果方案过程中发现需求本身有问题：
1. 在 spec 的「备注」章节记录问题和建议
2. 状态改为「需求待确认」
3. 询问用户确认后再继续

### 发现技术不可行
如果分析后发现技术方案无法落地：
1. 在 spec 的「备注」章节记录原因和替代建议
2. 状态改为「需求待确认」
3. 与用户讨论是否调整需求范围或换技术路径

## 注意
- 方案要落到 **具体文件和接口**，不要泛泛而谈。
- 涉及多端时，明确每端各自的改动，不要混在一起。
- 若需求与现实冲突（接口不存在、结构不符等），先把假设和待确认点写进 spec 的「备注」，再问用户，而不是自行假设。
- 若需求涉及埋点但 `specs/tracking-events.md` 缺失或本 spec 涉及埋点未定义，先按合理假设出方案，在 spec「备注」标注「埋点定义待补」风险。
- **明确标注「不在范围内」**，避免范围蔓延。
