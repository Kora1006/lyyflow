# /lyyflow:prd —— 需求拆分阶段

## 本地知识边界(.lyyflow-local/)

> **核心约定**：教训、会话笔记等**本地沉淀**放在 `.lyyflow-local/`,**不入 git 远程、不进 ~/lyyflow-archives 归档**;`specs/` 下的 `lessons-learned.md` 是公开快照,可被团队查看。

在 `/lyyflow:prd` 启动时**先跑 Bootstrap**(首次运行或项目根缺 `.lyyflow-local/` 时):

1. 在项目根建立 `.lyyflow-local/` 目录,内含 `lessons-learned.md`(本地私有版)+ `notes/`(会话笔记)。
2. 把 `/.lyyflow-local/` 写入该项目 `.git/info/exclude`(本地级 gitignore,**只对这个 clone 生效**,不入仓库本身)。
3. 在 `.git/hooks/pre-commit` 写入 lyyflow-managed-block 段(幂等),拦截 `git add -f` 强制添加 `.lyyflow-local/` 的提交。
4. 跑 `git ls-files .lyyflow-local/` 安全检查 —— 若有输出 → 已泄露,提示用户 `git rm -r --cached .lyyflow-local/` 后重跑。

后续 spec 开发中,所有教训沉淀都双写:`.lyyflow-local/lessons-learned.md`(主版本,Source of Truth)+ `specs/lessons-learned.md`(公开快照,默认同步,用户后续手动编辑决定哪些可发布)。

## 输入
`$ARGUMENTS` 是需求来源，按类型读取：
- **本地文件**（`.md`/`.txt`/`.docx`/`.pdf`）→ 用 Read 读取（PDF 直接传路径）
- **禅道 / 网页 URL** → 用 WebFetch 抓取正文
- **纯文本需求** → 直接作为需求内容

如果 `$ARGUMENTS` 为空，**先问用户索要需求来源，不要臆造**。

## 目标
把整份需求拆成 **粒度合适、可独立开发与验收** 的功能点（spec），并标注每个 spec 涉及哪些端/项目。本阶段**只做需求拆分，不写技术方案、不写代码**。

## 断点续跑机制

> 借鉴自 `yd-ai-wf.js` 的 `[x]` 标记机制。

如果 `specs/overview.md` 已存在：

1. **读取已有 spec 状态**：检查 spec 列表中的状态列
2. **跳过已完成的 spec**：状态为「已完成」的 spec 不再重新生成
3. **续接未完成的 spec**：只处理「待方案」状态的 spec

**快速路径**：如果所有 spec 都已完成，提示用户「需求已全部完成，如需新增需求请重新运行」。

## 执行步骤

### 阶段零：项目环境确认（重要）

在开始需求拆分前，先确认涉及项目的环境信息：

#### 1. 识别涉及的项目/仓库

根据需求内容初步判断涉及的端（H5、小程序、后台、服务端等），列出项目路径。

#### 2. 检查/增量生成 CLAUDE-RULE.md

对每个涉及的项目，检查其根目录是否存在 `CLAUDE-RULE.md`：

**增量模式判断**：

| 情况 | 处理方式 |
|------|----------|
| 不存在 | 询问用户是否生成，用户同意后新建 |
| 已存在且完整 | 通读了解，跳过生成（省 token） |
| 已存在但缺章节 | 只追加缺失章节，不覆盖已有内容 |

**询问流程**（仅在缺失时）：
> "检测到以下项目缺少 CLAUDE-RULE.md（项目规则文件）：
> - 项目A：xxx路径
> - 项目B：xxx路径
>
> 是否现在生成？生成后将分析项目结构、技术栈、约定等，便于后续方案设计。"

**生成内容覆盖**：
- 项目结构
- 技术栈与版本
- 目录与命名约定
- 公共组件/工具
- 接口请求方式
- 状态管理
- 规范/约束
- **末尾双引用**：`@.lyyflow-local/lessons-learned.md`（主版本，Source of Truth,本地私有,优先读）+ `@specs/lessons-learned.md`（公开快照，团队可见,兜底）—— 实现自学习闭环

#### 3. 创建自学习闭环文件（双路径）

> 借鉴自 `yd-ai-wf.js` 的 AGENTS.md 机制 + 本地知识边界约定。

**主版本（Source of Truth，本地私有，不入 git）**：在项目根 `.lyyflow-local/lessons-learned.md`（如不存在）：

```markdown
# 项目踩坑与教训（本地私有版，不入 git）

> 本文档是 Source of Truth，记录本地开发者踩过的所有坑。
> 公开快照同步在 specs/lessons-learned.md，由用户后续手动编辑决定哪些可发布。
> ⚠️ 本文件不进 ~/lyyflow-archives 归档（由 lyyflow runArchive 强制排除）。

---

## 累计教训：0 条

（暂无，后续 spec 完成后会自动追加）
```

**公开快照（团队可见，可被 archive 复制）**：在 `specs/lessons-learned.md`（如不存在）：

```markdown
# 项目踩坑与教训（公开快照，主版本在 .lyyflow-local/）

> 本文档由 lyyflow 自动同步 .lyyflow-local/lessons-learned.md 的内容。
> 由用户手动编辑决定哪些教训可发布给团队；本地主版本始终是 Source of Truth。

---

## 累计教训：0 条

（暂无）
```

#### 4. 记录项目信息

在 `specs/overview.md` 中记录已确认的项目及其 CLAUDE-RULE.md 状态。

### 阶段一：需求理解与拆分

1. 通读需求，提炼：需求背景、核心目标、目标用户、主要业务场景。

2. **识别涉及的端/项目**：H5、小程序、App、后台管理、服务端/API 等，逐端列出大致改动范围。

3. 将需求拆分为多个 spec，遵循：
   - 单个 spec 可独立完成、独立验收
   - 标注【涉及端】和【项目/仓库】
   - 标注【依赖】（哪个 spec 必须先做）
   - 每条都有可核验的【验收标准】
   - 验收标准使用 checkbox 格式：`- [ ] 标准1`

### 阶段二：接口文档询问与收集

> 在生成详细技术方案之前，必须确认接口文档是否就绪。接口文档是技术方案的核心输入，缺失会导致方案无法落地。

**询问流程**：

1. **询问用户是否有相关接口文档**：
   > "在生成技术方案之前，需要确认接口文档情况：
   > 1. 是否已有现成的接口文档？（如有，请提供文档路径或 URL）
   > 2. 如果没有现成接口文档，是否需要新增接口？"

2. **根据用户回答分支处理**：

   **分支 A：用户有现成接口文档**
   - 让用户提供文档路径或 URL
   - 用 Read/WebFetch 读取文档内容
   - 在 `specs/overview.md` 中记录接口文档来源
   - 继续进入阶段三

   **分支 B：用户没有现成接口文档，但不需要新增接口**
   - 在 `specs/overview.md` 中标注「无新增接口需求」
   - 继续进入阶段三

   **分支 C：用户需要新增接口**
   - 进入「接口文档创建流程」（见下方）

**接口文档创建流程**：

当用户表示需要新增接口时：

1. **分析需求中涉及的接口清单**：
   - 根据需求拆分结果，列出所有涉及的新增接口
   - 按 spec 归类，标注每个接口属于哪个 spec

2. **创建接口文档模板文件**：
   - 文件路径：`specs/api-contracts.md`
   - 使用下方「接口文档模板」生成初始内容
   - 包含：接口名称、请求方式、路径、请求参数、响应结构（均留空待填）

3. **通知用户填写**：
   > "已创建接口文档模板：`specs/api-contracts.md`
   >
   > 请在文件中填写完整的接口信息：
   > - 请求参数（字段名、类型、必填、说明）
   > - 响应结构（字段名、类型、说明）
   > - 其他业务约束（如鉴权、限流等）
   >
   > **填写完成后回复「已填写」或「继续」**，我将读取文档并继续生成技术方案。"

4. **等待用户确认**：
   - 用户回复「已填写」或「继续」后，用 Read 读取 `specs/api-contracts.md`
   - 验证接口文档是否填写完整（关键字段不为空）
   - 如有缺失，提示用户补充；完整则进入阶段三

### 阶段三：埋点需求询问与收集

> 在生成详细技术方案之前，必须确认埋点需求是否就绪。埋点定义是技术方案的核心输入，缺失会导致埋点遗漏或编码时临时拍脑袋。

**询问流程**：

1. **询问用户是否有相关埋点需求**：
   > "在生成技术方案之前，还需要确认埋点需求情况：
   > 1. 是否已有现成的埋点文档/需求？（如有，请提供文档路径或 URL）
   > 2. 如果没有现成埋点文档，是否需要新增埋点？"

2. **根据用户回答分支处理**：

   **分支 A：用户有现成埋点文档**
   - 让用户提供文档路径或 URL
   - 用 Read/WebFetch 读取文档内容
   - 在 `specs/overview.md` 中记录埋点文档来源
   - 继续进入阶段四

   **分支 B：用户没有埋点需求**
   - 在 `specs/overview.md` 中标注「无新增埋点需求」
   - 继续进入阶段四

   **分支 C：用户需要新增埋点**
   - 进入「埋点文档创建流程」（见下方）

**埋点文档创建流程**：

当用户表示需要新增埋点时：

1. **分析需求中涉及的埋点事件清单**：
   - 根据需求拆分结果，列出所有涉及的新增埋点事件
   - 按 spec 归类，标注每个事件属于哪个 spec
   - 区分事件类型：曝光（EXP）/ 点击（CLK）/ 其他

2. **创建埋点文档模板文件**：
   - 文件路径：`specs/tracking-events.md`
   - 使用下方「埋点文档模板」生成初始内容
   - 包含：埋点格式说明、按 spec 分组的事件定义（均留空待填）

3. **通知用户填写**：
   > "已创建埋点文档模板：`specs/tracking-events.md`
   >
   > 请在文件中填写完整的埋点信息：
   > - 事件编码（key，从埋点平台获取）
   > - 页面ID（pageId，从埋点平台获取）
   > - 模块ID/功能ID（如有）
   > - 动态属性（attr）的具体字段和取值来源
   > - 触发时机和触发位置
   >
   > **填写完成后回复「已填写」或「继续」**，我将读取文档并继续生成技术方案。"

4. **等待用户确认**：
   - 用户回复「已填写」或「继续」后，用 Read 读取 `specs/tracking-events.md`
   - 验证埋点文档是否填写完整（key、pageId 等必填字段不为空）
   - 如有缺失，提示用户补充；完整则进入阶段四

### 阶段四：生成拆分产物

1. 将产物写入当前项目的 `specs/` 目录：
   - `specs/overview.md`：总览（需求标题、来源、端清单、所有 spec 编号与名称、依赖关系、状态看板、接口文档来源、埋点文档来源、执行计划、blockers）
   - `specs/lessons-learned.md`：自学习闭环文件
   - `specs/tracking-events.md`：埋点文档（如涉及新增埋点）
   - 每个 spec 一个文件 `specs/spec-NNN-<短名>.md`，使用下方模板
2. 输出拆分摘要给用户，并询问是否需要调整粒度或补充验收标准。

  },
  common: {
    page: {
      pageId: "0iRBuc0Bp0",   // 页面Id(必填)
    },
  },
});
```

> 新功能统一使用此格式。如项目旧代码中存在其他格式（如 trackerEventCode + eventType），新埋点仍用上述格式。

## 执行计划

> 借鉴自 `yd-ai-wf.js` 的并行组规划机制。

### 自动并行组划分

根据依赖关系，spec 可分为以下并行组：

| 组别 | spec 列表 | 说明 |
|------|-----------|------|
| 组1（可并行） | spec-001, spec-002 | 无依赖，可同时执行 |
| 组2（依赖组1） | spec-003 | 依赖 spec-001 完成 |
| 组3（依赖组1） | spec-004 | 依赖 spec-002 完成 |

## 注意
- 多端需求：同一功能在不同端的差异要拆成独立 spec 或在 spec 内清晰分节标注。
- 状态字段统一用：`待方案` → `待实现` → `待 review` → `已完成`（或 `待修复`/`方案待修正`/`需求待确认`），与后续 /lyyflow:specs、/lyyflow:ai、/lyyflow:review 对齐。
- **接口文档是技术方案的前置依赖**，缺失接口文档不得跳过询问环节。如用户明确表示"暂无接口文档，先出方案"，需在 `specs/overview.md` 中标注风险，并提示后续补充。
- **埋点文档是技术方案的前置依赖**，缺失埋点文档不得跳过询问环节。如用户明确表示"暂无埋点文档，先出方案"，需在 `specs/overview.md` 中标注风险，并提示后续补充。
- **CLAUDE-RULE.md 提前生成**，避免后续阶段重复分析项目结构。
- **断点续跑**：重跑时跳过已完成的 spec（`[x]` 标记），续接未完成的。
- **增量模式**：生成文件时检查是否已存在，已存在则只追加缺失内容，不覆盖。
